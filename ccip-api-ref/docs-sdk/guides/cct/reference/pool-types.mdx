# CCT pool types and version support

The EVM CCT operations work with several token pool contract types across five pool versions (v1.5.0, v1.5.1, v1.6.0, v1.6.1, and v2.0.0). Version v1.6.0 applies only to `SiloedLockReleaseTokenPool`, the one pool the 1.6.0 release stamped; every other type reports v1.5.x, v1.6.1, or v2.0.0. What the SDK can *deploy* is narrower than what it can *administer and read*: new pools are always v2.0.0, while the read and configuration operations recognize older pools too. Use these matrices to pick a deployable type and to check whether an operation applies to a given pool.

## Deployable and recognized pool types

`deployTokenPool` and the [TokenPoolFactory](../evm#alternative-deploy-via-tokenpoolfactory) deploy v2.0.0 pools only. The read and administration operations recognize all seven pool types across every supported version.

| Pool type | `deployTokenPool` | Factory | Administer / read |
| --- | --- | --- | --- |
| `BurnMintTokenPool` | Yes (v2.0.0) | Yes (v2.0.0) | v1.5.0 to v2.0.0 |
| `BurnFromMintTokenPool` | Yes (v2.0.0) | No | v1.5.0 to v2.0.0 |
| `BurnWithFromMintTokenPool` | Yes (v2.0.0) | No | v1.5.0 to v2.0.0 |
| `LockReleaseTokenPool` | Yes (v2.0.0) | Yes (v2.0.0) | v1.5.0 to v2.0.0 |
| `BurnToAddressTokenPool` | No | No | v1.5.0 to v2.0.0 |
| `BurnMintWithLockReleaseFlagTokenPool` | No | No | v1.5.0 to v2.0.0 |
| `SiloedLockReleaseTokenPool` | No | No | v1.5.0 to v2.0.0 |

## Operation applicability by pool version

A v2.0.0-only operation throws `CCTOperationUnsupportedError` when the resolved pool is older. The sender allowlist moved in v2.0.0 from the pool to its bound `AdvancedPoolHooks`; `applyAllowlistUpdates` and `getAllowlist` follow it for you. Read the pool version (`getTokenPoolState`) before calling a version-scoped operation.

| Operation group | Methods | Applies to |
| --- | --- | --- |
| Remote lanes | `applyChainUpdates` | All versions (declare the matching `version` shape) |
| Rate limits | `setChainRateLimiterConfigs` | All versions (`fastFinality` targets the v2.0.0 FTF bucket only) |
| Admin & pool registration | `registerAdmin`, `acceptAdmin`, `setPool`, ownership transfers | All versions |
| Reads | `getTokenPoolState`, `getTokenPoolRemotes`, `getTokenAdminRegistry` | All versions |
| Sender allowlist | `applyAllowlistUpdates`, `getAllowlist`, `getAllowlistEnabled` | All versions (the pool through v1.6.1; its bound `AdvancedPoolHooks` on v2.0.0) |
| Transfer fees & finality | `applyTokenTransferFeeConfigUpdates`, `setAllowedFinalityConfig`, `getFee`, `getTokenTransferFeeConfig`, `getAllowedFinalityConfig` | v2.0.0 only |
| CCVs & hooks | `deployAdvancedPoolHooks`, `updateAdvancedPoolHooks`, `getAdvancedPoolHooks`, plus the methods that take `poolAddress` and act on its bound hooks: `applyCCVConfigUpdates`, `getCCVConfig`, `getAllCCVConfigs`, `getRequiredCCVs`, `setPolicyEngine`, `getPolicyEngine`, `setThresholdAmount`, `getThresholdAmount`, `updateAdvancedPoolHooksAuthorizedCallers`, `getAllAdvancedPoolHooksAuthorizedCallers` | v2.0.0 only |
| Lockbox | `getLockbox` | v2.0.0 only |

## Siloed liquidity pools

`SiloedLockReleaseTokenPool` escrows liquidity per remote lane. Each siloed lane holds its own balance, isolated from the shared *unsiloed* bucket that serves every non-siloed lane. The SDK works with the unsiloed side only:

- `provideLiquidity`, `withdrawLiquidity`, `transferLiquidity`, and `setRebalancer` act on the **unsiloed** bucket and its rebalancer. On a siloed pool they measure available funds with `getUnsiloedLiquidity()`, not the pool's full token balance (which also holds every siloed lane's escrow), so a pre-flight matches what the plain `withdrawLiquidity(uint256)` can actually pay out.
- The contract also exposes per-lane operations: `provideSiloedLiquidity`, `withdrawSiloedLiquidity`, `setSiloRebalancer`, and `updateSiloDesignations`. These are **not exposed by the SDK**. To manage a specific lane's silo, call the pool contract directly.

The SDK does not deploy siloed pools (see the deploy matrix above): deploy one from the contract's creation code, then administer and read it with the SDK.
